# Progressive Web App

Reading Buddy PWA Phase 1 adds installability and a safe offline fallback. PWA
Phase 2A adds the user-driven Web Push foundation described in
`docs/PUSH_NOTIFICATIONS.md`. Offline writes and background synchronization
remain out of scope.

## Architecture

- The App Router manifest is generated by `src/app/manifest.ts` and served at
  `/manifest.webmanifest`.
- App icons live in `public/icons/`. The vector source is
  `public/icons/icon-source.svg`.
- The service-worker source is `src/app/sw.ts`.
- `src/app/serwist/[path]/route.ts` uses `@serwist/turbopack` to build and serve
  the worker at `/serwist/sw.js` with root scope.
- `src/app/layout.tsx` registers the worker through `SerwistProvider` only in
  production. Serwist navigation pre-caching is disabled.
- `src/app/~offline/page.tsx` serves the static fallback at `/~offline`.

The integration uses Serwist 9.5.13's official Turbopack route-handler mode.
That release supports Next.js 14 and newer and is tested here with Next.js
16.3.6. No webpack fallback is used.

## Cache Policy

The policy is intentionally conservative:

- Build-time precaching includes immutable Next.js static assets, public icon
  files, and the offline fallback.
- Runtime caching uses `CacheFirst` only for same-origin `/_next/static/*`
  requests. Entries are limited to 128 and expire after one year.
- All document navigations are `NetworkOnly`. A successful authenticated page
  response is therefore never stored by the service worker.
- Cross-origin resources, including Clerk-hosted resources, are not runtime
  cached.
- Mutation requests are not cached or queued. A failed offline mutation remains
  failed.

The following same-origin paths are explicitly `NetworkOnly`:

- `/api/*`, including analytics, reminders, and `/api/cron/reminders`
- `/__clerk/*`
- `/sign-in` and all nested routes, including sign-in OAuth callbacks
- `/sign-up` and all nested routes

The route checks are defined in `src/lib/pwa/cache-policy.ts` and covered by
automated tests.

## Offline Behavior

When a document navigation fails because the network is unavailable, Serwist
returns the precached `/~offline` page. The page states that changes cannot be
saved offline and provides a full-document retry. It does not display cached
user data or imply that a book, reading session, settings change, or reminder
change succeeded.

Restoring the network reloads the current page through Serwist's
`reloadOnOnline` behavior. A manual retry is also available.

## Installation

### Android and Desktop Chromium

1. Open the production site over HTTPS.
2. Use the browser's install icon or choose **Install Reading Buddy** from the
   browser menu.
3. Launch Reading Buddy from the installed app shortcut. It opens in standalone
   display mode.

Browser wording and install eligibility can vary by browser and operating
system.

### iOS and iPadOS Safari

1. Open the production site in Safari.
2. Tap **Share**.
3. Choose **Add to Home Screen**, then confirm **Add**.

The root metadata supplies the Apple touch icon, standalone capability, app
title, and default status-bar style. iOS installation and service-worker
behavior are not identical to Android or desktop Chromium.

## Service-Worker Updates

The worker script is served with `Cache-Control: no-cache, no-store,
must-revalidate`, and registration uses `updateViaCache: "none"`. Each app load
can therefore discover a new worker without relying on an HTTP-cached worker
script.

`skipWaiting` and `clientsClaim` are enabled. A new worker activates and takes
control immediately, but the app does not force an update reload, so there is no
reload loop. This is low risk for Phase 1 because page responses and private
data are network-only, while versioned Next.js assets are immutable.

## Development and Testing

Run the normal development server with:

```bash
pnpm dev
```

Service-worker registration is disabled in development to avoid stale local
caches. Test the production worker instead:

```bash
pnpm build
pnpm start
```

Then inspect `/manifest.webmanifest`, `/serwist/sw.js`, and `/~offline` in the
browser. In browser developer tools, verify the manifest, worker scope, cache
contents, and offline navigation fallback.

If a worker from a previous production-mode test still controls localhost:

1. Open browser developer tools.
2. In **Application > Service Workers**, unregister the worker.
3. In **Application > Storage**, clear site data.
4. Close installed localhost app windows and reload.

## Phase 1 Limitations

- No automated push reminder decisions, email fallback selection, or push retry
  queue. Phase 2A supports only explicit current-device test notifications.
- No background sync, IndexedDB data model, queued mutations, or offline
  reading-session writes.
- No private dashboard or analytics response caching.
- No custom install banner or native app-store packaging.
- The offline experience is a fallback page, not an offline-capable copy of the
  authenticated application.
